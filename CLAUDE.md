# CLAUDE.md

Multi-tenant Purchase Requests API: employees ask to spend money, approvers approve or reject.

**Stack:** NestJS 12 (ESM) · PostgreSQL 18 · Prisma 7 · Vitest · oxlint · Prettier · Node 22+

## Commands

```sh
docker compose up -d        # Postgres with prep_api and prep_api_test (user/password prep/prep)
npm run start:dev           # API at http://localhost:3000/api/v1
                            # Swagger UI at http://localhost:3000/api/docs (JSON at /api/docs-json)
npm test                    # unit tests (*.spec.ts)
npm run test:e2e            # e2e tests (*.e2e-spec.ts) against prep_api_test; needs Postgres running
npm run check               # typecheck, lint, format, unit and e2e — run before calling work done
npm run db:migrate          # create and apply a migration after editing prisma/schema.prisma
npm run prisma:generate     # then regenerate the client; Prisma 7 migrate no longer does it
npm run db:seed             # add dev tenants acme and globex, one user per role, password "password"

npx vitest run src/path/to/file.spec.ts                                   # one unit test file
npx vitest run --config ./vitest.config.e2e.ts test/some.e2e-spec.ts      # one e2e file
```

## How we work

### Red/green TDD

Every behaviour change starts with a failing test.

1. **Red:** write the smallest test for the next bit of behaviour. Run it and watch it fail, and check it fails for the reason you expect (not a typo, import error or missing database).
2. **Green:** write the least code that makes it pass. No extra branches, options or "while I'm here" changes.
3. **Refactor:** clean up with the tests green. Re-run them after each step.

Repeat in small loops. Do not write production code without a failing test that demands it. Bug fixes start with a test that reproduces the bug.

- Pure logic (state transitions, permission checks, query parsing) gets unit tests, colocated as `src/**/<name>.spec.ts`.
- Anything touching HTTP, validation, the database or transactions gets e2e tests in `test/*.e2e-spec.ts`, using a real Postgres. Do not mock Prisma.
- Test names describe behaviour in plain language: `it('rejects approval of your own request')`.

### KISS

Pick the simplest thing that works and is easy to read. Plain functions over classes, direct code over indirection, one obvious place for each thing. If a reviewer needs an explanation to follow it, simplify it.

### YAGNI

Build only what the current task needs. No speculative abstractions, generic helpers, config flags, extension points or "future-proof" layers. Three similar lines beat a premature abstraction. Delete unused code rather than keeping it around.

### Boring ways

Prefer the well-known, conventional solution over the clever one.

- Use NestJS and Prisma the way their docs show: modules, controllers, services, DTOs with `class-validator`, `prisma.$transaction`.
- You can look up library and framework docs (NestJS, Prisma, Vitest, class-validator, etc.) with the context7 MCP server before writing or changing code that uses them. These versions are recent and their APIs differ from older releases.
- Generate Nest pieces with the Nest CLI (`npx nest g module|controller|service <name>`) so files match the standard layout.
- Do not add a dependency without asking first. Standard library and existing deps come first.
- No custom frameworks, metaprogramming or novel patterns when a plain one works.

### Self-contained docs

Every doc, comment and README section must stand on its own. Do not cross-reference other docs (no "see SPEC.md §3", "as described in X", links to sections elsewhere). References rot when the target moves or changes; a self-contained doc stays true or is obviously stale.

- State the fact where it is needed, briefly, instead of pointing to where it lives.
- When you change behaviour, update the docs and comments that describe it in the same change.
- Code comments explain _why_, not _what_, and never point to external documents.

## Code conventions

- **ESM:** relative imports must end in `.js`, e.g. `import { AppModule } from './app.module.js'`.
- **Prisma client** is generated into `src/generated/prisma/` (git-ignored, regenerated by `npm install` and `npm run prisma:generate`). Import from `../generated/prisma/client.js`. Never edit generated files.
- **Prisma 7** uses the `@prisma/adapter-pg` driver adapter; the connection URL is configured in `prisma.config.ts`, not in `schema.prisma`.
- **App setup** (global `/api/v1` prefix, validation pipe, Swagger UI) lives in `src/app.setup.ts` and is shared by `main.ts` and e2e tests. E2E tests must call `configureApp(app)` so they run the real configuration.
- **Validation:** every request body and query uses a DTO. The global `ValidationPipe` whitelists and rejects unknown fields.
- **Swagger:** every endpoint is documented with `@nestjs/swagger` decorators so it can be tried out from Swagger UI: `@ApiTags` on the controller, `@ApiOperation` plus an `@ApiResponse` for each status it can return (including 400, 403 and 404), `@ApiBearerAuth()` on endpoints behind the auth guard, and `@ApiProperty` on every DTO field. An endpoint is not done until its Swagger docs match its behaviour.
- **Style:** Prettier (single quotes, trailing commas) and oxlint with `no-floating-promises` as an error. Await or explicitly handle every promise.
- **Vitest globals** are enabled; `describe`, `it`, `expect` need no import.

## Domain rules that every change must respect

- **Tenant isolation:** the tenant always comes from the authenticated user, never from client input. Every query is scoped by `tenantId`.
  `test/tenant-isolation.e2e-spec.ts` calls every guarded endpoint in the Swagger document as another tenant's admin and expects 404 for `{id}` routes and no foreign data in any response. A new resource with `{id}` routes needs a fixture id there, and a new endpoint that takes a body needs a valid body there.
- **Hidden vs forbidden:** a resource the caller cannot see (other tenant, someone else's draft) returns 404. A visible resource the caller may not act on returns 403.
- **Lifecycle:** `DRAFT → SUBMITTED → APPROVED | REJECTED`. Only drafts can be edited or deleted, only by their owner. Approved and rejected are final. Any other transition is refused.
- **Separation of duties:** nobody approves or rejects their own request. Rejection requires a reason.
- **Transitions** are dedicated action endpoints (`POST /purchase-requests/:id/submit|approve|reject`), never a status field update.
- **Audit:** every write and its audit log entry happen in one database transaction.
- **Concurrency:** two people acting on the same request at once cannot both succeed; guard transitions with a conditional update on the current status.
- **Money** is an integer in minor units (cents) plus a currency code. Never use floats.
- **Permission and transition rules** live in pure functions, separate from controllers and Prisma, so they can be unit-tested directly.
